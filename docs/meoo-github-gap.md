# BugMentor 秒悟版与 GitHub 版差异及同步计划

更新日期：2026-08-17

## 一、为什么保留两个版本

两个版本不是两个不同产品，而是同一个 BugMentor 的两种实现：

```text
共同产品目标
让 Python 初学者在分级引导下自己发现、解释并修复错误
        ↓
秒悟版：快速验证界面、流程和比赛展示体验
GitHub版：掌握真实前后端、模型调用、测试与部署能力
```

秒悟版适合快速试验产品交互，GitHub 版适合展示自主开发过程和完整工程链路。任何功能都必须分别验收，不能因为一个版本完成就默认另一个版本也完成。

## 三、秒悟版已经完成的核心闭环

```text
提交错误代码
→ 匹配 IndexError 场景
→ 五级提示逐步引导
→ 每级填写并提交判断
→ 获得反馈后解锁下一级
→ 修改代码
→ 规则模拟重新验证
→ 成功后解锁学习复盘
→ 再次修改则验证失效、复盘重新锁定
→ 刷新后恢复最新代码和状态
```

当前确定性验证支持的核心演示案例：

```python
numbers = [10, 20, 30]
print(numbers[3])
```

以下修改可以通过：

```python
print(numbers[2])
print(numbers[-1])
```

该验证属于静态预设规则模拟，不会在服务器执行 Python 代码。其他错误类型不能可靠识别时必须显示“不支持或无法判断”，不能误报成功。

## 四、今天发现并修复的状态问题

### 1. 原始代码、当前代码与验证代码混用

修复后明确区分：

```text
originalCode：首次提交的错误代码，一次会话内不可变
currentCode：编辑器中的最新代码
verifiedCode：最近一次执行验证时的代码快照
```

### 2. 刷新后回退到旧代码

修复方向：当前代码变化后立即写入本地，云端延迟同步；恢复时比较 `updatedAt`，旧云端状态不能覆盖较新的本地状态。

### 3. 修改已通过代码后复盘仍然解锁

正确状态转换：

```text
验证成功
→ solved = true
→ 复盘解锁

代码再次发生实质修改
→ verificationStatus = none
→ solved = false
→ 显示等待重新验证
→ 复盘立即锁定
```

这些问题说明多个布尔值如果没有统一的状态转换规则，很容易产生“等待验证但已解决”的矛盾界面。

## 五、下一步同步优先级

### P0：不消耗秒悟额度也能完成

- 冻结当前可用的 IndexError 演示流程，不再进行无目标修改
- 保存 TypeError 验证提示词，额度恢复后一次性实施
- 为秒悟版整理固定验收清单和演示脚本
- 为 GitHub 版设计验证状态数据结构与测试用例
- 准备两个版本的 README、隐私边界和比赛介绍差异

### P1：优先同步到 GitHub 主项目

- 引入 `originalCode`、`currentCode`、`verifiedCode`
- 实现 IndexError 直接索引的确定性规则验证
- 增加等待验证、验证失败和验证成功状态
- 验证成功后解锁复盘，再次修改后重新锁定
- 为上述状态转换编写自动化测试

### P2：额度恢复后完善秒悟版

- 增加字符串与整数拼接 TypeError 验证
- 测试 `str()`、f-string 和逗号分隔输出三种修复
- 防止删除输出语句或硬编码结果被误判成功
- 对 SyntaxError 和逻辑错误评估是否适合规则验证

### P3：比赛交付

- 发布秒悟在线应用并记录公开访问地址
- 部署 GitHub 版前端与后端
- 准备固定演示案例与故障备用录屏
- 分别整理秒悟赛与中兴赛的介绍重点

## 六、两场比赛的叙事重点

### 秒悟比赛

- 面向初学者的明确痛点
- 三栏交互与五级提示体验
- 修改后验证和复盘闭环
- 使用秒悟快速把想法变成可体验产品

### 中兴比赛

- React、FastAPI 与 DeepSeek 的完整技术链路
- Pydantic 输入校验和 AI 安全边界
- 自动化测试与工程质量
- 学生判断、动态反馈和可扩展验证引擎

## 七、维护规则

每次新增功能时记录四项：

1. 功能在哪个版本实现。
2. 是否已由人工实际验收。
3. 另一个版本是否需要同步。
4. README 和比赛材料应如何准确描述。

使用下面的完成定义：

```text
生成代码 ≠ 功能完成
构建通过 ≠ 产品正确
实际操作通过验收标准 + 状态刷新后仍正确 = 功能完成
```
