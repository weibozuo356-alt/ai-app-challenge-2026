# BugMentor 开发日志：Day 5——验证秒悟原型并完善配置与学习记录管理

## 二、今天理解的两个版本

今天同时接触了两个 BugMentor 版本，但它们的作用不同：

```text
秒悟平台原型
→ 快速验证页面布局、交互流程和产品体验
→ 使用平台生成的预设规则和云服务能力

GitHub 主项目
→ 自己维护 React、FastAPI 和 DeepSeek 代码
→ 用于理解技术链路、持续开发、测试和最终部署
```

秒悟不是等项目全部写完以后才使用的“提交入口”，它也可以在开发过程中帮助快速验证产品想法。但秒悟生成的代码不能自动替代主仓库，两边的功能需要分别确认，不能看到平台原型成功就认为 GitHub 版本也已经同步完成。

## 三、用验收标准检查 AI 生成结果

今天没有只看页面是否好看，而是给功能写出了明确的期望行为和验收标准。

例如下一级提示的规则是：

```text
进入当前提示等级
→ 下一级按钮默认禁用
→ 用户填写非空判断
→ 用户提交判断
→ 系统显示反馈
→ 下一级按钮解锁
```

进入新等级、重新提交代码或重置后，按钮必须重新禁用。

这让我理解：

> AI 生成了一个能打开的页面，不等于产品功能已经正确；必须通过具体操作验证状态变化是否符合预期。

## 四、五级提示的教学节奏

今天使用下面的案例测试提示流程：

```python
numbers = [10, 20, 30]
print(numbers[3])
```

预期结果是输出最后一个数字 30，实际报错为：

```text
IndexError: list index out of range
```

调整后的五级思路是：

1. 只引导阅读报错和定位出错行，不解释答案。
2. 观察访问表达式、使用的下标和列表实际元素数量。
3. 引导用户根据“索引从 0 开始”计算合法下标。
4. 引导用户思考最后一个合法下标与负索引两种方式。
5. 才给出完整原因、`numbers[2]`、`numbers[-1]` 和参考代码。

这体现了 BugMentor 的核心产品原则：提示不是越详细越好，而是应该在当前阶段只提供足够推动思考的信息。

## 五、环境变量与前端配置

原来前端请求地址直接写在代码里：

```text
http://127.0.0.1:8000
```

这只适合本机开发。部署后，后端地址会发生变化，因此今天改为：

```javascript
import.meta.env.VITE_API_BASE_URL
```

配置关系是：

```text
.env.local
→ Vite 启动时读取 VITE_API_BASE_URL
→ App.jsx 取得 API_BASE_URL
→ fetch 向正确的后端发送请求
```

`.env.local` 保存当前电脑的真实配置，并由 `*.local` 规则忽略；`.env.example` 可以提交到 GitHub，用来告诉其他开发者需要配置哪些变量。

前端的 `VITE_` 前缀变量会进入浏览器代码，因此只能保存公开配置，例如 API 地址，不能保存 DeepSeek API 密钥。真正的模型密钥仍然只能放在后端 `.env` 中。

## 六、学习记录的唯一 ID

以前 React 列表使用保存时间作为标识。如果两条记录恰好具有相同时间，可能产生重复标识。今天改为保存时调用：

```javascript
crypto.randomUUID()
```

为每条记录生成独立 ID。

旧记录没有 ID，因此读取时通过 `ensureRecordId()` 为它们补上兼容标识。这是一种数据迁移思路：增加新字段时仍然允许旧数据继续使用。

## 七、删除与清空记录

单条删除的逻辑是：

```text
点击删除
→ window.confirm() 二次确认
→ filter() 保留 ID 不等于目标 ID 的记录
→ 写回 localStorage
→ 更新 React 状态
→ 页面自动重新渲染
```

清空全部记录的逻辑是：

```text
点击清空
→ 二次确认
→ localStorage.removeItem()
→ React 状态设为空数组
→ 页面显示没有历史记录
```

这里的关键不是按钮，而是浏览器存储和 React 状态必须同时更新，否则刷新前后可能显示不一致。

## 八、语法正确不等于产品正确

增加清空按钮时，代码一度被放进了“本次学习记录”复盘表单，并把表单标题错误地改成了“历史学习记录”。

当时 ESLint 和生产构建仍能通过，因为 JSX 语法本身是合法的。但页面的产品含义不正确。

```text
Lint / Build
→ 检查语法、规则和能否生成产物

人工页面验收
→ 检查内容位置、交互含义和用户流程
```

因此自动化检查和人工验收缺一不可。

## 九、今天认识的专业名词

| 专业名词 | 我的理解 |
|---|---|
| Prototype | 用来快速验证产品想法和交互的原型 |
| Acceptance Criteria | 判断功能是否完成的一组明确条件 |
| State Transition | 用户操作后界面从一个状态变化到另一个状态 |
| Environment Variable | 在源代码之外提供可变化配置的方法 |
| API Base URL | 前端向后端发送请求时使用的基础地址 |
| Vite Environment Variable | 由 Vite 在构建或启动时注入前端的配置 |
| UUID | 用来唯一标识一条数据的随机标识符 |
| Backward Compatibility | 新版本仍能读取和使用旧版本数据 |
| Data Migration | 数据结构变化时对旧数据进行转换或补充 |
| Destructive Action | 删除或清空等可能造成数据丢失的操作 |
| Confirmation Dialog | 执行危险操作前要求用户再次确认的弹窗 |
| Semantic Bug | 代码能运行，但内容含义或业务位置错误 |

## Day 5 总结

今天不仅完善了学习记录功能，也第一次把 AI 平台当作产品原型和验收工具使用。我开始从“页面能不能显示”转向检查“用户必须经过哪些步骤、每一步应该看到什么、什么条件下按钮才能解锁”。

技术上，我理解了环境变量如何让同一套前端代码适配本地与部署环境，也理解了 UUID、旧数据兼容、删除确认、localStorage 与 React 状态同步之间的关系。最重要的是认识到：构建通过只能证明代码能够运行，真实产品还必须通过场景化验收来判断交互和教学逻辑是否正确。
