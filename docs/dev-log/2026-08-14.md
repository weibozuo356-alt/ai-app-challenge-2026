# BugMentor 开发日志：Day 4——完成学生追问、修改重试与分级提示硬约束

日期：2026-08-14

## 今日目标

把原来“AI 单向给提示”的流程升级为真正的教学对话：学生先说出自己的判断，AI 判断方向并继续追问；学生修改代码后可以重新检查。同时使用自动化测试与真实模型案例验证功能和提示分级。

## 一、今天完成了什么

- 在调试请求中增加 `student_response` 和 `previous_hint`
- 让后端区分普通提示 `hint` 与学生追问 `follow_up`
- 扩展系统提示词，使 AI 能判断学生思路并提出下一步问题
- 限制学生回答和上一条提示最多 2000 个字符
- 在前端增加“我的判断”输入框和“提交我的判断”按钮
- 在未开始、加载中和已解决状态下正确禁用相关按钮
- 将主按钮升级为“开始侦查 Bug / 重新检查修改后的代码”两种状态
- 保留当前提示等级，学生回答不会自动跳级
- 将后端自动化测试从 5 项增加到 7 项
- 完成 IndexError、SyntaxError、TypeError 三类真实模型案例验证
- 发现并修复一级提示提前定位代码的问题
- 通过后端测试、前端 lint 和生产构建检查

## 二、今天升级后的产品闭环

```text
用户提交代码和报错
→ AI 返回当前等级提示
→ 用户写下自己的判断
→ 前端发送学生回答和上一条提示
→ AI 判断正确、部分正确或需要调整
→ AI 在同一级继续追问
→ 用户修改代码
→ 重新检查修改后的代码
→ 找到问题并完成学习复盘
```

昨天的交互更接近：

```text
用户点击按钮 → AI 给提示
```

今天升级为：

```text
AI 提问 → 学生思考并回答 → AI 判断 → 继续引导
```

这使 BugMentor 从“分级答案生成器”更接近“调试教练”。

## 三、前端新增了什么状态

React 新增 `studentResponse`，保存用户在“我的判断”输入框中写下的内容。

```text
输入框 onChange
→ setStudentResponse()
→ studentResponse 状态更新
→ 点击提交
→ requestHint() 发送给后端
```

提交成功后清空输入框，避免用户误把同一个答案重复发送。

按钮还会根据状态变化：

- `hintLevel === 0`：尚未开始，不能提交判断
- `isLoading === true`：正在请求，暂时禁用按钮，避免重复调用
- `isSolved === true`：已经进入复盘，不再继续索取提示

这叫作基于状态的界面控制。

## 四、同一个接口为什么能支持两种操作

今天没有新建第二个 API，而是继续使用：

```text
POST /api/debug
```

请求中新增两个可选字段：

- `student_response`：学生本轮的判断
- `previous_hint`：AI 上一轮给出的提示

如果 `student_response` 为空，后端生成普通提示；如果不为空，后端返回追问反馈。

```text
student_response 为空  → interaction = hint
student_response 有内容 → interaction = follow_up
```

这个接口没有在服务器保存整段会话。对话所需的当前代码、上一条提示和学生回答由前端每次重新发送，因此它仍然是无状态接口。

## 五、为什么要发送上一条提示

如果只发送学生回答“我觉得是索引问题”，AI 不知道这句话是在回答什么问题。

加入 `previous_hint` 后，本轮上下文变成：

```text
代码与报错
+ 上一条 AI 提示
+ 学生回答
→ AI 可以判断回答是否对应问题
```

上一条提示和学生回答都属于不可信输入，只作为文本数据使用，不能改变系统提示词中的分级规则。

## 六、软约束与硬约束

最初只在系统提示词中写明：“一级提示不能定位具体代码。”这属于软约束，因为大语言模型仍可能不完全遵守。

真实测试 SyntaxError 时，AI 根据代码和完整报错猜出了缺失符号，说明功能能运行，但产品规则没有真正守住。

最终在 Python 代码中增加硬约束：第一次请求一级提示时，不向模型提供源代码正文和完整报错细节，只告诉模型引导用户自行观察。

```text
软约束：提示词要求模型不要泄露
硬约束：程序根本不把可泄露的信息交给模型
```

追问阶段会恢复必要上下文，使 AI 能判断学生主动提出的思路，但仍不能补充当前等级之外的答案。

这让我理解：系统提示词不能代替代码层的安全与权限控制。

## 七、输入长度为什么要限制

新增字段使用 Pydantic 限制为最多 2000 个字符：

```text
浏览器输入
→ FastAPI / Pydantic 校验长度
→ 合法才调用 DeepSeek
→ 超长输入直接返回 HTTP 422
```

这可以避免异常大请求占用服务器资源和模型额度。前端的 `maxLength` 改善用户体验，后端的 Pydantic 校验才是真正的安全边界，因为客户端限制可以被绕过。

## 八、TDD：红灯到绿灯

今天先写测试，规定 `/api/debug` 必须把学生回答和上一条提示传入 AI 服务，并返回 `interaction: follow_up`。

第一次运行测试时出现：

```text
KeyError: 'interaction'
```

这个失败是预期的红灯，证明旧代码还没有实现新行为。补充最小后端实现后，测试变绿。

```text
Red：先看到新行为测试失败
Green：写最少代码让测试通过
```

随后增加超长学生回答测试，确认接口返回 422，而且不会调用 AI 服务。

## 九、当前自动化测试

后端现在有 7 项测试：

1. 根接口正常返回 200
2. 调试接口成功返回 AI 提示
3. AI 服务失败时返回安全的 503
4. 空代码返回 422
5. 非法提示等级返回 422
6. 学生回答和上一条提示正确传给 AI 服务
7. 超过 2000 字的学生回答被拒绝，且不会调用 AI

测试结果：

```text
Ran 7 tests
OK
```

前端也通过：

```text
npm run lint
npm run build
```

## 十、真实模型案例验证

今天使用三种错误进行真实 DeepSeek 调用：

1. `IndexError`：一级提示后提交“索引 3 超出列表范围”的判断，AI 正确确认并继续追问，提示等级保持为 1。
2. `SyntaxError`：真实测试发现一级提示会提前推断缺失符号，因此增加代码层硬约束，复测后只引导用户阅读报错类型。
3. `TypeError`：一级提示只引导观察报错描述的数据类型，没有直接给修改答案。

这里体现了两类测试的区别：

```text
自动化测试：验证接口结构、校验、异常和稳定行为
真实模型测试：验证提示质量、教学节奏和模型是否遵守规则
```

两种测试不能互相替代。

## 十一、今天新认识的专业名词

| 专业名词 | 我的理解 |
|---|---|
| Follow-up | 根据学生上一轮回答继续判断和追问 |
| Conversation Context | 当前对话所需的上一条提示、学生回答等上下文 |
| Stateless API | 服务器不保存会话状态，每次请求携带本轮所需信息 |
| Interaction Mode | 本次响应属于普通提示还是追问反馈 |
| State-driven UI | 页面按钮和内容根据 React 状态变化 |
| Soft Constraint | 通过提示词要求模型遵守，但不能完全保证的规则 |
| Hard Constraint | 通过程序限制数据或能力，模型无法绕过的规则 |
| Data Minimization | 只把完成当前任务所需的最少数据发送给外部服务 |
| Trust Boundary | 外部数据进入系统、需要校验与限制的位置 |
| Abuse Case | 从误用或攻击角度设计的测试场景 |
| TDD | 先写失败测试，再写最少实现使其通过 |
| Red / Green | 测试先失败，再因正确实现而通过 |

## 十二、今天真正学到的连接逻辑

```text
React 状态保存学生回答
→ fetch 把状态序列化为 JSON
→ HTTP POST 发送到 FastAPI
→ Pydantic 校验字段类型和长度
→ main.py 判断交互类型并调用 AI 服务
→ ai_service.py 组织受约束的模型上下文
→ DeepSeek 生成当前等级反馈
→ FastAPI 返回 JSON
→ React 更新 coachMessage
→ 页面显示 AI 的判断与追问
```

每一层职责不同：

- React 负责交互和页面状态
- HTTP / JSON 负责前后端传输
- FastAPI / Pydantic 负责接口和边界校验
- AI 服务层负责组织模型上下文与调用 DeepSeek
- 自动化测试负责防止后端行为回退
- 真实案例负责判断教学体验是否符合产品目标

## Day 4 总结

今天 BugMentor 从 AI 单向给提示，升级为学生能够回答、AI 能够判断并继续追问的双向调试教练。修改后的代码也可以重新提交，形成“提示—思考—修改—验证”的学习闭环。

最重要的收获不是多了一个输入框，而是理解了前端状态、HTTP JSON、Pydantic 请求模型、AI 上下文和模型反馈如何串成一次对话；也通过真实案例认识到，提示词只是软约束，关键教学规则需要用代码建立硬边界。
