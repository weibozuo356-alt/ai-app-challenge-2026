# BugMentor 开发日志：Day 6——完成 IndexError 验证闭环并梳理双版本差异

日期：2026-08-17

## 今日目标

今天继续完善秒悟平台版 BugMentor，重点不是增加更多页面，而是建立“修改代码后验证是否修复”的完整闭环，并通过刷新、再次编辑和复盘锁定等真实操作检查状态是否一致。

## 一、今天完成了什么

- 为秒悟版增加修改后重新验证入口
- 为 IndexError 直接列表索引场景增加预设规则验证
- 验证 `numbers[2]` 和 `numbers[-1]` 两种正确修复
- 增加验证成功、验证失败和等待重新验证三种反馈状态
- 明确提示代码没有在服务器执行，结果来自预设规则模拟
- 验证成功后自动标记解决并解锁学习复盘
- 代码再次修改后使旧验证结论失效
- 修复再次修改后复盘没有锁定的问题
- 修复刷新后回退到上一版代码的问题
- 增加原始代码、当前代码和验证代码三种快照
- 增加本地即时保存、云端延迟同步和时间比较恢复逻辑
- 发现代码与报错不一致时验证器无法定位原错误的边界情况
- 设计 TypeError 字符串与整数拼接验证需求，但因秒悟额度用完暂缓实施
- 梳理秒悟平台版与 GitHub 主项目的功能差异和同步计划

## 二、今天完成的产品闭环

```text
提交原始错误代码
→ 进入五级提示
→ 用户填写自己的判断
→ 获得反馈后解锁下一提示
→ 用户修改代码
→ 系统检查代码是否发生实质变化
→ 使用预设规则模拟验证
→ 失败：保持提示进度并继续修改
→ 成功：标记解决并解锁复盘
→ 再次修改：旧成功失效并重新锁定复盘
```

这比“点击按钮获得提示”更接近一个真正的学习产品，因为用户需要把理解落实到代码修改，并接受一次新的验证。

## 三、为什么需要三种代码快照

今天最重要的数据结构是：

```text
originalCode：首次提交、确实产生错误的代码
currentCode：编辑器里用户现在看到的代码
verifiedCode：最近一次被规则验证的代码
```

如果只有一个 `code` 字段，就无法同时回答：

- 原来的错误是什么？
- 用户现在改成了什么？
- 当前成功结论对应的是哪一版代码？

刷新错误正是因为这些含义曾经混在一起：当前代码覆盖了原始代码，或者旧云端代码覆盖了新本地代码，导致验证器找不到原来的越界表达式。

## 四、验证状态机

当前验证状态可以理解为：

```text
none：尚未验证，或验证后代码再次发生变化
failed：最近验证的代码仍包含问题
passed：最近验证的代码通过当前规则
```

关键状态转换：

```text
none → 点击验证 → failed / passed
passed → 修改代码 → none
failed → 修改代码 → none
任意状态 → 重置或新会话 → 初始状态
```

复盘是否解锁不能只看曾经是否成功，而必须看当前代码是否仍对应最新成功验证。

## 五、人工验收发现的问题

### 1. 提交内容与报错不一致

第一次测试时，原始代码只提交了列表定义，没有提交真正出错的 `print(numbers[3])`。验证器无法在原始代码中找到越界访问，因此不能比较修改前后。

这不是规则失效，而是输入数据不完整。后续可以把提示优化为：

```text
未在原始代码中找到与报错对应的索引访问，请确认提交的是产生该报错的完整代码。
```

### 2. 刷新后验证成功变成失败

原因包括缺少 `verifiedCode`、当前代码污染 `originalCode`、旧数据兼容错误以及本地云端覆盖顺序不清楚。

### 3. 修改正确代码后复盘仍然开放

页面一度同时显示“等待重新验证”和“问题已解决”。这说明验证状态与 `solved` 没有作为一次完整状态转换更新。

修复后的原则是：

```text
代码改变 → 旧结论失效 → solved=false → 复盘锁定
```

## 六、本地与云端同步

为避免用户输入后立即刷新造成丢失：

```text
代码变化
→ 立即写入本地缓存
→ 延迟同步云端
```

刷新时：

```text
先恢复本地最新状态并显示
→ 再异步读取云端
→ 比较 updatedAt
→ 只有更晚的数据才能覆盖
```

这种问题叫作竞态条件：多个异步操作完成顺序不同，旧请求可能在更晚返回后覆盖新状态。因此不能简单地“谁最后返回就使用谁”。

## 七、规则验证与真实执行的区别

当前秒悟版不会运行 Python，只做静态文本规则检查。

优点：

- 不执行不可信代码，安全边界简单
- 响应快，适合固定演示案例
- 结果确定，便于测试

限制：

- 不能证明任意 Python 程序真的运行正确
- 只能支持已经设计过的错误场景
- 无法识别时必须返回“不支持或无法判断”，不能猜测成功

因此页面必须持续标明“预设规则模拟，代码未在服务器执行”。

## 八、秒悟额度用完后的决策

TypeError 验证提示词已经设计完成，但继续生成需要新的平台额度。今天没有因此充值或仓促修改，而是暂停秒悟生成，转向：

- 保存待实施需求
- 冻结已经稳定的 IndexError 演示
- 梳理双版本差异
- 规划哪些能力应同步到 GitHub 主项目
- 准备不消耗额度的文档、测试和演示工作

这是范围管理：资源不足时优先保护已经完成的核心功能，不让项目因为追求更多功能而重新变得不稳定。

## 九、今天认识的专业名词

| 专业名词 | 我的理解 |
|---|---|
| Validation Engine | 根据明确规则判断修改是否满足修复条件的模块 |
| Code Snapshot | 某一时刻代码内容的固定副本 |
| State Machine | 规定状态以及状态之间合法转换的模型 |
| Derived State | 根据其他权威状态计算得到的界面状态 |
| Race Condition | 多个异步操作顺序不确定导致结果错误 |
| Debounce | 等输入暂时停止后再执行同步，减少频繁请求 |
| Last-write-wins | 根据更新时间选择较新数据的一种冲突策略 |
| False Positive | 实际未修复却被规则错误判定为成功 |
| Inconclusive | 现有规则无法可靠判断，而不是成功或失败 |
| Scope Management | 根据时间和资源选择必须完成与暂缓功能 |

## Day 6 总结

今天的收获不是又多了一个按钮，而是第一次真正处理跨刷新、跨保存和再次编辑的状态一致性问题。我理解了为什么原始代码、当前代码和已验证代码必须分开，也理解了验证成功不是永久结论：代码发生变化后，旧结论必须失效，复盘也要重新锁定。

秒悟额度用完没有让工作停止。我们把开发切换到文档、差异管理和 GitHub 版同步设计，保护已经完成的核心闭环，并为下一次有限额度的使用提前准备更精确的需求。
