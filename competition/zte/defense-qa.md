# BugMentor 答辩问答题库

## 1. BugMentor 与直接问通用大模型有什么不同？

通用大模型往往优先给答案，BugMentor 把教学约束写进产品流程：前四级只给渐进线索，学生必须提交判断并收到反馈才能继续，第五级才展示完整答案；修复后还要验证和复盘。核心差异是“调试学习闭环”，而不仅是一次对话。

## 2. 为什么选择五级提示？

五级对应观察报错、定位位置、理解规则、形成修改方案和核对完整答案。层级足够表达认知递进，同时不会让初学者在过多步骤里失去耐心。按钮锁定把这个教学顺序变成可验证的产品行为。

## 3. 如何降低 AI 幻觉风险？

AI 负责解释和追问，确定性环节由代码规则控制：提示等级、答案保护、表单约束、支持类型验证和复盘解锁都不依赖模型自由发挥。知识卡链接到 Python 官方文档；界面也明确标注静态验证边界。

## 4. “修改后验证”真的运行了 Python 吗？

没有。当前版本出于安全和开发范围考虑，使用静态规则模拟验证 IndexError、TypeError 和特定 SyntaxError，并在界面明确提示“代码未在服务器执行”。因此不会把规则结果包装成真实运行结果。

## 5. 为什么不直接在服务器执行学生代码？

任意代码执行需要容器隔离、资源配额、超时、网络与文件系统限制以及滥用防护。当前比赛版优先保证教学闭环和边界透明。后续若引入沙箱，会把执行服务设计成独立、最小权限、可审计模块。

## 6. 数据和隐私如何处理？

调试请求只发送当前代码、预期结果、报错、提示等级和当前判断；API Key 只保存在后端环境变量。学习记录、复习统计和 JSON 导出默认在浏览器 localStorage 完成，不要求登录，也不发送完整历史到 AI 后端。

## 7. 如何保证 API Key 不泄露？

前端只配置后端公开地址，不包含 DeepSeek Key；密钥存储在 Render 服务端环境变量。仓库、日志和公开文档都不写入真实密钥，后端异常也返回通用错误而不是堆栈。

## 8. 工程质量如何证明？

项目有 35 项前端测试和 12 项后端测试，覆盖状态恢复、提示锁定、三类验证规则、异常输入、CORS 和安全响应。GitHub Actions 在每次推送时自动运行测试、Lint、生产构建和依赖检查；线上还有健康检查和冒烟脚本。

## 9. 为什么目前只重点支持三类错误？

比赛版先把 IndexError、TypeError、SyntaxError 做成完整、可演示、可测试的闭环，而不是铺开很多浅层模板。架构已把演示案例、验证器、知识卡和复习建议解耦，后续可按同一接口扩展 AttributeError、KeyError 和课程自定义案例。

## 10. 怎样体现“专业课助教”，而不是普通纠错工具？

它不只指出错误，还要求学生表达判断，提供官方知识依据，记录根本原因与预防措施，并基于历史高频错误生成复习计划和迁移练习。这些功能对应专业课中的形成性评价、错题复盘和知识迁移。

## 11. 教师能从中获得什么价值？

当前学生端减少教师重复解释基础报错的时间，并让学生带着结构化复盘来提问。后续教师端可配置课程案例、查看匿名聚合的高频错误、针对薄弱知识点布置练习，但必须先补齐授权、去标识化和数据治理。

## 12. 如何衡量教学效果？

可关注首次修复成功率、平均提示等级、重复错误率、复盘完成率和迁移题正确率。比赛版已经能记录错误类型和复盘，后续在获得明确同意后再增加匿名统计，避免为了指标过度收集数据。

## 13. 服务不可用时怎么办？

前端会给出可理解的错误提示，不泄露内部信息；学习历史仍保留在本地。现场演示会提前唤醒 Render，并准备本地运行、正式文档、关键截图和备用录屏四层兜底。

## 14. 项目的主要局限是什么？

验证器不是通用 Python 解释器，AI 提示质量受模型和输入影响，localStorage 不适合跨设备同步，当前缺少教师端和真实教学对照实验。文档会明确这些边界，后续路线是安全沙箱、教师用例库、更多错误类型和经同意的学习分析。

## 15. 项目是否原创，第三方依赖是否合规？

产品交互、前后端实现、验证规则、测试和文档由参赛者完成；使用 React、Vite、FastAPI、DeepSeek 等公开技术与服务，并在 README、合规说明和依赖文件中说明用途。公开材料不声称第三方模型或框架为自研。
